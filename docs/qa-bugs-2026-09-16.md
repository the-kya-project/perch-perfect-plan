## Open bugs

### BUG-1 — Dead sitter link renders loading skeletons forever (highest impact)

**Severity:** high — affects non-account users with no way to self-diagnose.

After the owner deletes their account (and, by the same code path, when a token is revoked
or expired), the sitter link renders **permanent skeleton placeholders**. There is no error
state, no "this link no longer works" message, and nothing in the console.

Reproduced twice, on fresh loads:
- `GET /sitter/<token>` → **HTTP 200** (SSR shell)
- no console errors, no failed network requests
- UI never leaves its loading state

The token lookup evidently resolves to something the UI treats as "still loading" rather
than "not found", so the not-found branch never renders. Sitters have no account and no
context — they just see a page that appears to hang.

**Expected:** a plain, friendly terminal state, e.g. "This link is no longer active. Ask
[owner] for a new one."

**Repro:** create a sit (or open the owner Review-step preview, which mints a real token),
copy the sitter URL, delete the owner account, reload the URL.

### BUG-2 — Pluralization: "1 item need details"

**Severity:** low (copy) · **Location:** `src/routes/_authenticated/birds/$birdId.setup.tsx:1251`

```jsx
{incomplete.count} item{incomplete.count > 1 ? "s" : ""} need details. Add the brand, amount, and timing for: {...}
```

Pluralizes the noun but not the verb, so a single incomplete item reads **"1 item need
details."** Visible in the care-plan wizard whenever exactly one food item is incomplete —
a common case, and on a path App Review would walk.

**Fix:** `item{n > 1 ? "s" : ""} need{n > 1 ? "" : "s"} details`.

### BUG-3 — Hardcoded female pronoun: "How she steps up"

**Severity:** low–medium (copy correctness; user-visible to sitters) · **Locations:**
- `src/lib/sitter.functions.ts:155` — **sitter-facing**
- `src/routes/_authenticated/birds/$birdId.setup.tsx:2342`

```js
{ key: "step_up", column: "clip_step_up_path", label: "How she steps up" }
```

The string is a hardcoded literal in both places and there is no pronoun helper anywhere in
the codebase. Every bird gets "she" regardless of the **Sex** field the app explicitly
collects (Unknown / Male / Female). Observed with Sex = Unknown.

**Fix:** use the bird's name ("How ZZ Test Bird steps up") or neutral phrasing ("How they
step up"). Both call sites must change together.

### BUG-4 — Raw Postgres errors are shown to users (27 sites, no sanitizer)

**Severity:** medium — UX plus mild schema disclosure, and it reaches public surfaces.

Database errors are passed verbatim to `toast.error()`. Observed live:

> `insert or update on table "birds" violates foreign key constraint "birds_owner_id_fkey"`

`grep -rn "toast.error(error.message" src/` returns **27 call sites**, and there is no
`friendlyError` / `humanizeError` / `mapSupabaseError` helper anywhere in the codebase — so
any DB-level failure (FK, constraint, RLS, connection) surfaces raw, including table and
constraint names.

Worth prioritising because some of these are **public, unauthenticated** surfaces:
`src/routes/handoff.$token.tsx:170` (handoff recipients), plus the sitter components.

**Fix:** one mapper that turns Supabase errors into human copy, log the raw error, and show
a generic fallback for anything unrecognised.

### BUG-5 — Stale session after remote account deletion lands in onboarding

**Severity:** low–medium (edge case, but reachable and confusing).

When an account is deleted **elsewhere** — another device, or admin action — a device still
holding the session does not detect it. On relaunch the app shows the onboarding **Welcome**
screen with no name (the profile is gone) and lets the user walk into "Add a bird". Submitting
then fails with the raw FK error from BUG-4.

Deleting through the app on the *same* device is handled correctly (signs out, clear toast) —
this is specifically the cross-device / server-side case.

**Expected:** detect the invalid session (the user row is gone) and sign out to the auth
screen with a brief explanation.

**Repro:** sign in on the device, delete the user server-side, relaunch the app.

## Minor observations (decide, not necessarily fix)

- **Names are optional at signup.** Submitting an empty form jumps validation straight to
  EMAIL, skipping first/last name — yet `profiles.display_name` / `full_name` /
  `first_name` are derived from them. A user can create an account with no name at all.
  Intentional? If so, confirm the empty-name rendering everywhere a display name is shown.
- **NL truncates the bird name** in the sitter-preview header ("ZZ Test B…") because
  "Oppasperiode actief" is wider than "Sit active". Cosmetic i18n layout squeeze.
- **`persistBirdPhoto` silently falls back to storing base64 in Postgres.**
  `src/lib/birdPhoto.ts:60` — `catch { return photoUrl; }`. If the Storage upload fails,
  the megabyte-sized `data:` URL is persisted into `birds.photo_url` instead. That is
  exactly what the file's own header says the design exists to avoid ("keeps the
  megabyte-sized image bytes OUT of Postgres rows, so list queries stay tiny"). Rare and
  lossless, but it would quietly bloat rows and slow the dashboard with no signal.
- **The owner's Review-step sitter preview writes a real `sits` row** (`sitter_name:
  "__preview__"`, `notes: "Owner preview"`, token expiring 23:59:59 same day). By design —
  the preview needs a token — but it means `sits` accumulates preview rows over time. Worth
  knowing before anyone counts sits as a usage metric.

## Investigated and cleared (NOT bugs)

Recorded so nobody re-chases them.

- **Tour shows "Willow's hatch day" / "Sam arrives tomorrow" on a brand-new account.** Looks
  like a data leak; it is hardcoded demo content in `src/lib/tourDemo.ts` (`demo-willow`,
  `demo-sit`, `demo-hatch`). Demo mode tears down correctly on Skip — verified the real
  empty state returns.
- **Confirm-email screen doesn't auto-advance** when the address is confirmed directly in
  the DB. It waits for a **session** via `onAuthStateChange`; the emailed link supplies one.
  Correct behavior.
- **`routine_tasks.time_of_day` is NULL** on derived tasks. Timing lives in `category`
  (`morning`/`evening`); `derived` carries `{kind, params, labelKeys}` for localization.
- **"Create sit & generate link" appeared to do nothing** with empty dates. The guard exists
  — `SitForm.tsx:262` fires `toast.error("Pick a start and end date.")`. The toast had
  dismissed before the screenshot. Not a silent no-op.
- **Apple sign-in failing while other apps worked** was not the user's Apple ID (a
  first-time sign-up on an unrelated app succeeded). It was the stale App ID registration.

## Second pass (media, foster, health check, lifecycle)

**Verified working**

- **Bird photo upload.** iOS PHPicker (limited "only the items you select" access — no
  full-library permission). Stored as a Storage *path* (`<ownerId>/<uuid>.jpg`, 427 KB
  JPEG in `bird-photos`), never base64. Crop/reposition supported. Renders via signed URL.
- **EXIF/GPS is stripped.** The picker warns "Location Is Included", but
  `src/lib/imageUpload.ts:55` re-encodes through `canvas.toDataURL("image/jpeg", quality)`
  before upload, which drops all EXIF. Coordinates never reach Storage. Good outcome —
  recorded so nobody has to re-derive it.
- **Foster intake.** `is_foster: true` persists; Home segregates fosters into a separate
  **"In your care — 1 foster"** section with a Foster pill and "With you since <date>",
  while "Your flock" correctly reads "No birds yet".
- **Health check.** Full questionnaire; submit validation scrolls to the first unanswered
  question, outlines each in red, and shows inline "Please answer this before submitting".
  Live triage preview ("Preview: GREEN — Nothing concerning logged"). Writes `daily_logs`,
  and the optional weigh-in flows straight into `weight_entries` (402 g, source `owner`)
  exactly as the copy promises.
- **Cold launch while signed in lands on Home**, not the sign-in screen — the historically
  fragile redirect path behaves.
- **Explore tab** renders mission, community waitlist, and live blog content from Webflow.
- Notification badge increments after a health check.
- Health-check copy uses "themselves" (neutral), which confirms BUG-3's hardcoded "she" is
  an oversight rather than house style.

**Cleanup lesson (process, not a product bug)**

Deleting a test account **through the app** left zero orphans — `deleteMyAccount` purges
Storage. Deleting the second account **via SQL** bypassed that and stranded its bird photo:

```
bird-photos/c011b118-59bb-4f25-956d-9547caa68984/098543af-c8e3-47e3-8dff-780a1ab421aa.jpg
```

Supabase refuses direct deletion from `storage.objects`
("Direct deletion from storage tables is not allowed. Use the Storage API instead."), so it
needs removing from the dashboard. **Always delete test accounts through the app.** This is
a plausible origin for some of the 22 pre-existing orphaned objects.

email), clip record/upload (no camera in the simulator), Android parity beyond auth,

## Open bugs

### BUG-1 — Dead sitter link renders loading skeletons forever (highest impact)

**Severity:** high — affects non-account users with no way to self-diagnose.

After the owner deletes their account (and, by the same code path, when a token is revoked
or expired), the sitter link renders **permanent skeleton placeholders**. There is no error
state, no "this link no longer works" message, and nothing in the console.

Reproduced twice, on fresh loads:
- `GET /sitter/<token>` → **HTTP 200** (SSR shell)
- no console errors, no failed network requests
- UI never leaves its loading state

The token lookup evidently resolves to something the UI treats as "still loading" rather
than "not found", so the not-found branch never renders. Sitters have no account and no
context — they just see a page that appears to hang.

**Expected:** a plain, friendly terminal state, e.g. "This link is no longer active. Ask
[owner] for a new one."

**Repro:** create a sit (or open the owner Review-step preview, which mints a real token),
copy the sitter URL, delete the owner account, reload the URL.

### BUG-2 — Pluralization: "1 item need details"

**Severity:** low (copy) · **Location:** `src/routes/_authenticated/birds/$birdId.setup.tsx:1251`

```jsx
{incomplete.count} item{incomplete.count > 1 ? "s" : ""} need details. Add the brand, amount, and timing for: {...}
```

Pluralizes the noun but not the verb, so a single incomplete item reads **"1 item need
details."** Visible in the care-plan wizard whenever exactly one food item is incomplete —
a common case, and on a path App Review would walk.

**Fix:** `item{n > 1 ? "s" : ""} need{n > 1 ? "" : "s"} details`.

### BUG-4 — Raw Postgres errors are shown to users (27 sites, no sanitizer)

**Severity:** medium — UX plus mild schema disclosure, and it reaches public surfaces.

Database errors are passed verbatim to `toast.error()`. Observed live:

> `insert or update on table "birds" violates foreign key constraint "birds_owner_id_fkey"`

`grep -rn "toast.error(error.message" src/` returns **27 call sites**, and there is no
`friendlyError` / `humanizeError` / `mapSupabaseError` helper anywhere in the codebase — so
any DB-level failure (FK, constraint, RLS, connection) surfaces raw, including table and
constraint names.

Worth prioritising because some of these are **public, unauthenticated** surfaces:
`src/routes/handoff.$token.tsx:170` (handoff recipients), plus the sitter components.

**Fix:** one mapper that turns Supabase errors into human copy, log the raw error, and show
a generic fallback for anything unrecognised.

### BUG-5 — Stale session after remote account deletion lands in onboarding

**Severity:** low–medium (edge case, but reachable and confusing). **Status: fixed and verified.**

When an account is deleted **elsewhere** — another device, or admin action — a device still
holding the session does not detect it. On relaunch the app shows the onboarding **Welcome**
screen with no name (the profile is gone) and lets the user walk into "Add a bird". Submitting
then fails with the raw FK error from BUG-4.

Deleting through the app on the *same* device is handled correctly (signs out, clear toast) —
this is specifically the cross-device / server-side case.

**Expected:** detect the invalid session (the user row is gone) and sign out to the auth
screen with a brief explanation.

**Repro:** sign in on the device, delete the user server-side, relaunch the app.

**Fixed and VERIFIED end to end — `c56abd2`.** This was committed unverified on the first
pass because a hand-inserted `auth.users` row could not be signed in (GoTrue returned
"Database error querying schema"). **That failure was my own provisioning bug, not a GoTrue
limitation:** GoTrue scans `confirmation_token`, `recovery_token`, `email_change`,
`email_change_token_new`, `email_change_token_current`, `phone_change`, `phone_change_token`
and `reauthentication_token` into non-nullable Go strings, so they must be `''`, never NULL.
Set to `''` (plus a matching `auth.identities` row with `provider='email'`), a directly
provisioned account signs in normally — no confirmation email sent, so no hard bounce against
the project's sender reputation.

With that, the real repro ran: signed in as a throwaway, confirmed the dashboard rendered,
deleted the `auth.users` row via SQL while the browser held a live unexpired JWT, reloaded.
Result: title went `Home` → `Sign in`, URL `/auth`, and `localStorage` auth-token keys were
`[]`. The account had been used for a full pass beforehand (bird, weight, journal, meds, vet
summary, many reloads) with no spurious sign-out, which is the regression evidence.

### BUG-7 — "Save as PDF" does nothing in either native app (App Store risk)

**Severity:** high for resubmission. A visibly non-functional control is the kind of thing
App Review flags under guideline 2.1, and this is on a surface the listing describes.

`birds/$birdId.vet-summary.tsx` implemented "Save as PDF" as `onPress={() => window.print()}`.
Inside the Capacitor shells that call does nothing at all:

- **iOS.** `window.print()` in a `WKWebView` requires the host app to implement WebKit's
  print delegate. Grepped `node_modules/@capacitor/ios` and `ios/App/App/AppDelegate.swift`
  for `printFrame` / `UIPrintInteractionController` / `WKUIDelegate` — **zero hits in either**.
  No delegate, no print, no error.
- **Android.** `WebView` does not implement `window.print()` at all; printing requires
  `PrintManager` through a JS interface, which this app does not have.

So the button worked only in a desktop or mobile browser. It is now hidden when
`isNativeApp()` is true; the browser keeps it. **Share is unaffected** — `navigator.share`
*is* supported in `WKWebView` — so there is still a way to get the sheet to a vet.

**Root cause of the confusion:** a full `@react-pdf/renderer` implementation
(`src/lib/vetSummaryPdf.tsx`, lazy-loaded, iOS share-sheet download) was written on
2026-06-29 but **never merged**. It lives only on branch `today-wip-backup`, commit
`43fd077`; `git merge-base --is-ancestor 43fd077 HEAD` returns false. That branch also
carries sit/journal deletes, a landing reframe, shared `CarePlanView`, app/member
onboarding and scan photos — **none of which should be assumed shipped.**

**Decision needed:** port the react-pdf work from `today-wip-backup` (web-only, so it reaches
installed binaries via Vercel with no rebuild — the preferred route), or implement the iOS
print delegate (native, requires a new binary). Hiding the button is an interim, not the fix.

Fixed (interim): `0845923`.

## Security headers — resolved 2026-09-17 (`f46f291`)

- **SEC-1 (CSP did nothing) — FIXED.** The policy was report-only *and* had no `report-uri`
  or `report-to`, so it blocked nothing and recorded nothing. Added the collector at
  `/api/public/csp-report` and pointed both directives at it. **The policy is still
  report-only on purpose** — do not flip it to enforce until the collector has seen about a
  week of real traffic. Enforcing a policy nobody has observed is how you break production,
  and the whole point of report-only is to find out first. Watch Vercel logs for
  `[csp-report]`.
- **SEC-2 (`'unsafe-inline'` in `script-src`) — DEFERRED, deliberately.** Removing it needs a
  per-request nonce, which interacts with the pre-hydration cold-launch script (the fix for
  signed-in owners landing on sign-in). That is a real change to first paint and is not
  something to do days before a resubmission. It is also moot until SEC-1 is enforcing.
  Revisit after the CSP is enforced.
- **SEC-3 (HSTS) — FIXED.** Vercel was sending `max-age=63072000` with no `includeSubDomains`;
  added. Scoped to `app.thekyaproject.com` it covers only hosts *under* `app.*`, not the apex
  or `www` (separate site), so it is safe. **`preload` deliberately not set** — it is a
  one-way door, removal takes months, and it would commit the apex domain.

## Security headers (production, verified 2026-09-16)

Present and sensible: `referrer-policy: strict-origin-when-cross-origin`,
`x-content-type-options: nosniff`, `x-frame-options: SAMEORIGIN`,
`permissions-policy: camera=(self), microphone=(self), geolocation=(), browsing-topics=()`
(geolocation correctly disabled, consistent with EXIF being stripped on upload).

**SEC-1 — CSP is report-only AND has no reporting endpoint.** The header is
`content-security-policy-report-only` with a thorough, well-scoped policy — but there is no
`report-uri` or `report-to` directive anywhere in it. So it does not block anything
(report-only) and does not record anything either. It is currently decorative. This also
explains why PostHog's `$csp_violation` event has never been seen: nothing reports to it.

To flip it to enforce safely you need violation data first. Either add a `report-to`
endpoint and collect for a week, or accept the risk and enforce directly — but "report-only
until we verify" is not achieving anything in its present form.

**SEC-2 — `script-src` includes `'unsafe-inline'`.** That defeats most of CSP's XSS value.
It may be required by the pre-hydration inline head script used for the cold-launch redirect
fix; if so, a nonce or hash would keep the protection. Worth deciding deliberately rather
than inheriting.

**SEC-3 — HSTS has no `includeSubDomains` or `preload`.** `max-age=63072000` (2 years) is
good; the missing directives leave subdomains uncovered.
